What this site is

This is an independent publication, not a product site. One person writes and maintains it, and it reflects a specific way of working: treat the model as a capable colleague with no memory of yesterday, then write everything down as though the next reader knows nothing. Most of what is here began as a private note written after a session went wrong — a brief that was too vague to fail, a handoff that dropped a file path, an agent that reported success on work it had not done.

The library is organised by task, not by tool. Each guide starts from something a person actually has to do this week: write a brief a model cannot misread, decide what belongs in a handoff packet, redact a config file before it goes into a chat window, review generated output before publishing it, or tell the difference between software that runs on your machine and software that only says it does. Where a template helps, the whole template is on the page and you can copy it. Where something has a limit, the guide names the limit instead of writing around it.

The second half of the site is reference material for the LYGO project family, the local-first tooling these guides are built on. The Continuum verifier turns “done” into claims you can re-run against real files. The champion pages describe fifteen authored personas and say plainly that they are prompt frameworks, not authorities. The LLM console and SkillHub document software you can carry on a disk and run offline. None of it is presented as magic, and every tool page states what the tool does not do.

There is no email gate, no account, and no “unlock the rest” prompt. Guides, tools, games, and the archive read end to end without signing in. Hosting is covered by optional donations and, when approved, labelled advertising; neither one gets a say in what a page concludes.

Who it is for

The guides assume a reader with a real task and limited patience. They are not written for people collecting prompts, and they are not written for people who want to be told that AI will fix everything.

People who run agents for real work

You already point a coding agent, a chat model, or a local model at something that matters, and you have met the failure this site is named after: the work looks finished, the summary sounds confident, and then a file underneath is missing. The material here assumes you can open a terminal and read a diff. It does not assume a team, a budget, or a research library behind you. Everything can be tried on one laptop in an evening.

Writers, teachers, and reviewers

If part of your job is explaining AI work to other people — a class, a client, a compliance reviewer — start with the human review checklist, the redaction workflow, and the editorial standards. They are written as procedures you can hand to someone else, not as essays to admire. The tools tour exists for the same reason: it describes what each free tool is for and what it will not do, so you can decide in a minute whether it belongs in your workflow.

Curious newcomers

You do not need the vocabulary to begin. The lattice overview opens with the problem the project cares about, defines six words that unlock the rest of the site, and gives you three tasks of roughly twenty minutes each. Leave the tool pages alone on a first pass; they will make more sense after the guides.

Who it is not for

This is not a benchmark site, a model-release news feed, or a place to stockpile prompt packs. If you want a leaderboard, the vendors publish better ones than anyone else can. What gets tested here is practice: what to ask for, what to write down, how to check the result, and what to do when the result is wrong.

Three habits the guides keep returning to

Read three guides and a pattern appears. Almost every failure on this site traces back to one of three places: a brief that could not fail, a handoff that carried a story instead of evidence, or a completion claim that nobody re-checked. Each habit below is a section of the site's thinking, with the guide that goes deeper.

1. Brief before you build

A useful brief has six blocks: goal, why now, inputs, constraints, done checks, and handoff. The block that does the actual work is done checks. A check that cannot fail is a wish. “The page looks good” is a wish. “The page loads at 390 px, every internal link resolves, and the prose count is above 700” is a check, because a reviewer can run it and get a no. The second most valuable block is constraints, especially the negative ones: do not change the default behaviour, do not add a dependency, do not rewrite the parts that already work. A brief with no constraint of that shape invites collateral edits, and collateral edits are how a small job becomes a review problem.

Write better AI task briefs carries the copy-paste template and three worked examples — a documentation brief, a code brief, and a review brief — each with the reason it is shaped that way.

2. Hand off with evidence, not vibes

When a session ends, the next reader inherits whatever you left behind. If that is a chat summary, they inherit a story. The alternative is a packet: the files that changed, the exact commands that were run, the output of those commands, what is still open, and who owns the next step. The handoff playbook uses a deliberately small status vocabulary — done, done-with-caveat, blocked, parked — because the distance between “finished” and “finished except the part I could not test” is the distance between an honest handoff and a trap. The playbook includes a file map, a worked example, the five failure modes worth watching for, and a thirty-minute drill with pass/fail marks, so a team can practise the handoff before it matters.

3. Re-check “done”

An exit code proves a process finished. It does not prove the file changed, that the test covered the change, or that the feature works for anyone but the agent that wrote it. Continuum is the site's answer: a capsule of claims — this file exists, it contains this string, it has this SHA-256, this JSON path equals “ok” — that you seal when the work is complete and re-run later. If something changed after the seal, verify reports drift, and drift is the useful signal, because either the world moved for a legitimate reason or the claim was never true. The done-claims guide walks the mental model and the ethics; the browser portal does the hashing locally, so you can check a capsule someone sent you without uploading their files anywhere.

How these pages are made

Every guide carries a human byline and a review date. AI helps with drafting, outlining, editing, and checking a draft against a source. It does not get a byline, and it does not get to invent a source, a date, a hash, or a test result. A byline here is not a claim that no tool was used; it is a claim that a person is accountable for what shipped. The full commitment — what is published, what is refused, how corrections work — is on the editorial standards page.

Technical claims have to be re-runnable. When a guide says a command works, the command was run. When it says a file contains something, the check is on the page. When a room is unreachable, the page says it is unreachable instead of filling the gap with a story. Time-sensitive claims carry a date and an invitation to re-check them, because a price, a licence, or a default can change under a page that has not moved.

Before a page publishes it passes a structural gate: a minimum amount of original prose, a real introduction, required metadata, valid structured data, working internal links, and a consent notice. Ads are allowed only on pages with enough prose to stand on their own, and never on tools, games, policy pages, error pages, or thank-you pages. The gate exists because a page that repeats a template across a dozen URLs is not a library; it is one article wearing costumes, and it gets treated as a quality failure.

What is not published here: scraped or spun articles, manufactured reviews or testimonials, undisclosed paid placements pretending to be editorial, pages that exist only to carry an ad, and instructions for wrongdoing or unauthorised access. When a page is wrong, it is fixed in place and the review date moves. If a correction changes the argument, the page says what changed instead of quietly deleting the old claim.

Δ9 champions: fifteen authored roles

Each champion is a persona framework with a job. LYRΔ keeps continuity and memory. Δ9RA challenges a claim and demands the receipt. ARKOS maps a system before anyone touches it. JUSTICAE asks who is affected. KAIROS asks what happens first. Lightfather holds the publishing ethic. They exist because a role changes what a model notices: the same question asked of a challenger and of a builder produces different work, and knowing which one you wanted is half the skill.

They are creative frameworks for structuring a conversation, not professionals, not authorities, and not supernatural anything. They are not a substitute for a lawyer, a doctor, an accountant, or a reviewer with domain knowledge. The honest way to use one is to pick a single role for a single task, paste the full invoke text rather than a nickname, and keep the output so the next person can see which role produced which claim. The summon guide covers preparation, five steps, quality checks, and the common mistakes.

Games

Nineteen browser games, no account and no install: an isometric island war, a hex-grid command game, a play-money trading floor, golf with markers and wind, a rally ghost to beat, a pixel dungeon, a 3D chess board, and a city builder among them. They load in the tab and save locally.

They are on this site because building them is how several of these lessons were learned. A game is a system whose failures are visible in ten seconds: the collision that only fails on one tile, the control that inverts under a camera, the save that works until it does not. The Arcade Deck is the console view — preview any title, launch it, then read the hall of results that other players left behind.

LYGO Signal and the radio rooms

The Signal archive holds forty-eight episodes: essays that argue a position, roundtables written as conversations between the project's personas, and serialised fiction set in the same world. They are authored pieces, not transcripts of a live event, and the episode pages say which kind you are reading. Recurring subjects are ethical AI design, local-first sovereignty, systems thinking, and the seams where those meet.

Two players sit beside the archive. LYGO Radio streams the station's own recordings around the clock from the same catalogue the game halls draw on — free, no login, no DRM. AI Talk Radio is the studio: you write an episode brief on any topic, and two hosts voice it in your browser with a caller hotline and a timecoded transcript you can keep. Both pages explain what is live and what is an experiment; neither pretends to be a broadcast network.

FAQ

Is everything free?

Yes, for guides and on-site tools. There is no paywall, no account, and no required email address. Optional donations support hosting, and labelled advertising appears when AdSense approves the site. Tip jar: PayPal.me/ExcavationPro · Patreon.

Do I need the full LYGO stack to use this site?

No. The guides are written for someone with a browser and a text editor. The stack pages exist for readers who decide they want the local tools, and they say what the install actually costs before you start. Nothing on the site requires you to run any of it.

Are the champions magic, or do they really do something?

They are authored personas and prompt frameworks, and that is the honest description. What they really do is change what a model pays attention to: a challenger role produces objections, a builder role produces plans. What they do not do is grant knowledge, authority, or judgement that the model did not already have.

Who is responsible for AI output that comes from these tools?

You are, if you publish or deploy it. The human review checklist exists because a model can produce a confident page with a fabricated citation in it, and no tool on this site will catch that for you. Continuum proves a file matched a hash; it does not prove the argument is sound.

How is the site funded, and will ads change what it says?

Hosting is paid for by the author and by optional donations; advertising is a secondary, labelled layer that may appear once approved. Ads do not control conclusions, sponsors do not get to edit a review, and there are no undisclosed paid placements. The editorial standards spell this out, including what happens if a page is ever wrong.

Who writes the pages?

Justin Helmer, with AI assistance on drafting and checking. The byline means a person reviewed the page and is accountable for the claim, the links, and the date — not that no tool was used. Every page carries a review date, and a material correction moves that date.

Can I quote or teach from these guides?

Quoting a paragraph with attribution and a link back is fine, and teachers are welcome to use the checklists in a class. For anything larger — reprinting a whole guide, translating one, or building a course around the material — use the contact page first so the answer is on the record.

Something here is wrong. What do I do?

Use the contact page with the URL and the sentence or step that is wrong. Corrections are welcome, and a factual error is treated as a bug rather than an embarrassment. For a security issue, describe the class of problem and ask for a safer channel before sending details.
